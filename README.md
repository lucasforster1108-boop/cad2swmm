# cad2swmm

**English** | [中文](README.zh.md) | [한국어](README.ko.md) | [日本語](README.ja.md)

I do building drainage design for a living. Every project ends the same way:
the CAD drawing is finished, and then I sit in SWMM typing manholes, pipes,
diameters and invert levels all over again — data that is already in the
drawing. After one too many rounds of that, I wrote this.

cad2swmm reads a DXF drainage drawing and writes a SWMM `.inp` file you can
open and run in EPA SWMM 5. That is all it does, but it removes the worst
hour of the job. The other SWMM tools on GitHub all start from GIS data;
engineers don't draw drainage networks in GIS, so the CAD step was missing.

The water-supply side of the same annoyance lives here too. `cad2epanet.py`
does the identical job for EPANET — DXF water-supply drawing in, runnable
EPANET 2.2 `.inp` out. It used to be its own repo (cad2epanet); it has been
merged into this one, because the two converters share most of their
machinery: the DXF reading, endpoint snapping and label matching now live
in one shared module, `dxfnet.py`, and each script keeps only its own
model's semantics.

```bash
pip install ezdxf
python cad2swmm.py my_network.dxf -o my_network.inp
```

## What it reads from the drawing

- Manholes: blocks, points or circles on the node layers become junctions
  (and outfalls)
- Node names and invert levels come from block attributes (`ID`, `INV` /
  `IL` / `ELEV`) or from text like `IL=12.34`
- Pipes: lines and polylines on the pipe layers become conduits, with the
  length measured from the actual geometry
- Diameters come from `DN300` / `D300` / `Φ300` / `300mm` labels near a pipe
- Flow direction follows the inverts, high to low

If a pipe endpoint doesn't snap to a manhole, it creates a node for it.
Anything it had to guess — a missing diameter label, a missing invert — is
printed as a warning naming the pipe or manhole it belongs to. It does not
quietly invent numbers.

## Try it

The `examples` folder has a small 5-node, 4-pipe network drawn the normal
way (the DXF is generated, so run the first command first):

```bash
python examples/make_example.py
python cad2swmm.py examples/example.dxf -o examples/example.inp

# if your drawing is in millimetres, and you want a 50 L/s test inflow
python cad2swmm.py site.dxf -o site.inp --scale 0.001 --design-flow 50
```

The example converts to:

```
nodes: 5 (junctions 4 + outfall OUT1)
conduits: 4, total length 115.0 m
```

There are three test scripts, because I wanted proof rather than a screenshot.
`tests/validate.py` checks the structure (lengths, diameters, flow
directions). `tests/run_swmm.py` runs the generated file in the real EPA
SWMM engine through pyswmm: the 50 L/s design inflow routes end to end,
peak at the outfall is about 54 L/s including dynamic-wave effects, and the
flow-routing continuity error stays under 0.1%. `tests/run_pipeline.py`
verifies the full pipeline below — all three products generated, and the
numbers in the report checked against the .rpt itself.

## Full pipeline: drawing → simulation → check report

Conversion is only the first step. With `--pipeline` the same script walks
the rest of the way: it runs the `.inp` in the real SWMM engine via pyswmm,
then turns the `.rpt` into a Chinese check report (Markdown) — continuity
error graded, outfall loading summarised, flooded/surcharged nodes and
full pipes listed, every number taken verbatim from the .rpt.

```bash
pip install pyswmm
python cad2swmm.py examples/example.dxf --pipeline --outdir examples/pipeline --design-flow 50
```

The files in `examples/pipeline/` (`example.inp`, `example.rpt`,
`example_校核报告.md`) are the real output of that exact command. The steps
also work individually: `--run` only simulates, `--report` only writes the
report. If you already have a `.inp` or `.rpt`, pass the file as input to
use just the later stages:

```bash
python cad2swmm.py model.inp --run --report
python cad2swmm.py model.rpt            # check report only
```

The report is generated by the vendored `swmm_report_cn/` package in this
repo (from swmm-report-cn, MIT, pure standard library — no extra install).

## cad2epanet: the water-supply side

```bash
python cad2epanet.py my_water_network.dxf -o my_water_network.inp
```

What it reads from the drawing:

- Nodes: blocks, points or circles on the node layers become junctions,
  reservoirs and tanks
- Names and ground elevations from block attributes (`ID`, `ELEV` / `EL` /
  `INV` / `IL`) or text like `EL=52.30`; base demand from the `DEMAND`
  attribute (L/s)
- Source: a node with `TYPE=RESERVOIR`. Its total head comes from the
  `HEAD` attribute, or elevation + `--source-head` when there is none —
  printed as a warning, not hidden. No source marked at all: the highest
  node is used, also with a warning
- Tanks: `TYPE=TANK` nodes, with levels and diameter from the `--tank-*`
  options
- Pipes and diameters are read exactly as on the drainage side

One real difference from drainage: supply is pressurised, so pipes are
**not** oriented by elevation — a pipe just connects two nodes and EPANET
works out which way the water flows.

The same small example exists for water (`examples/make_example_epanet.py`
generates `example_epanet.dxf`):

```bash
python examples/make_example_epanet.py
python cad2epanet.py examples/example_epanet.dxf -o examples/example_epanet.inp
```

```
nodes: 5 (junctions 4 + reservoir R1)
pipes: 4, total length 115.0 m
total base demand: 16 L/s
```

Two more test scripts cover this side. `tests/validate_epanet.py` checks
the structure and that every junction connects back to the reservoir;
`tests/run_epanet.py` runs the generated model in the real EPANET engine
through WNTR: the reservoir supplies exactly 16.00 L/s, matching the total
base demand, and junction pressures land at 11.95–14.93 m — the small head
loss you would expect over 115 m of pipe at that flow.

Options that differ from cad2swmm (`--scale`, `--snap`, `--node-layers`,
`--pipe-layers`, `--default-diameter` work the same):

```
--default-elevation 0.0    fallback ground elevation (m) when no EL text is found
--roughness-c 130          Hazen-Williams C (130 = new cast iron / DI)
--reservoir J9             source node name (else TYPE=RESERVOIR, else highest node)
--source-head 10           head (m) added to elevation when a reservoir has no HEAD
--tank-diameter 10         diameter (m) for TYPE=TANK nodes
--tank-init-level 2        initial level (m) for TYPE=TANK nodes
--tank-max-level 5         max level (m) for TYPE=TANK nodes
```

## Options

```
--scale 0.001         drawing units -> metres (0.001 if the drawing is in mm)
--node-layers 井,MANHOLE   layers that hold manholes/nodes
--pipe-layers 管线,PIPE    layers that hold pipes
--default-diameter 0.3     fallback diameter (m) when no DN label is found
--default-invert 0.0       fallback invert elevation (m)
--outfall J9               name of the outfall node (else: lowest node)
--roughness 0.013          Manning's n (default: concrete pipe)
--design-flow 50           add a constant inflow (L/s) at the highest junction
--snap 2.0                 endpoint-to-node snap tolerance (drawing units)
--pipeline                 full pipeline: convert -> run -> Chinese check report (implies --run --report)
--run                      run the .inp in the SWMM engine (pyswmm), producing a .rpt
--report                   generate a Chinese check report (.md) from the .rpt
--outdir DIR               directory for pipeline products (.inp/.rpt/report)
--report-output PATH       explicit path for the check report .md
```

## How to draw so it works

Keep drawing the way you already draw. The defaults recognise both English
and Chinese layer conventions:

- Nodes: block references, points or circles on layers like `MANHOLE`,
  `NODE`, `检查井`, `井`
- Pipes: lines / polylines on layers like `PIPE`, `SEWER`, `管线`, `管道`,
  `排水`
- Outfall: a node block with attribute `TYPE=OUTFALL`, or pass `--outfall`
- DWG files: save as DXF in your CAD package first (or batch-convert with
  ODA File Converter)

## What it doesn't do yet

- Read DWG directly
- Subcatchments and rainfall — you still delineate those yourself
- Pumps, valves and dual (sewer + storm) systems
- On the EPANET side: demand patterns and extended-period simulation —
  the generated model is a single steady-state snapshot; no pump curves,
  control valves, fire flow or water-quality runs

It also works as an agent skill (see `SKILL.md`) in tools that support
SKILL.md, such as Claude Code and DeepSeek Harness: drop it in and say
"turn this CAD drawing into a SWMM model".
